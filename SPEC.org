#+TITLE: T3 Code fork: actors and waves
#+OPTIONS: num:t

This file specifies what this fork adds to T3 Code. Everything it does not mention is upstream's and is left alone. Upstream's own terms are defined in [[file:docs/internals/glossary.md][docs/internals/glossary.md]]; this spec uses them unchanged and defines only the terms the fork introduces.

* Objective Function
One window for all agent work.

A person who runs many long-lived agents should have each of them one click away, with a face they recognise, wherever they are in the app. The waves those agents start should be visible beside them, and what a wave is saying should be readable without leaving the thread in hand. Underneath, each provider keeps running exactly as upstream runs it.

The fork stays small enough to merge upstream every week or two without dread. Every feature is judged against that.

* Problem and Outcome
** Problem
- Long-lived threads are hard to keep in reach. With twenty or more of them, a list of titles does not scale: they are all "open", and finding one is a search.
- A wave of workers started by one agent has no shared place to talk that is not itself an agent, and no place in the window where a person can watch it.
- Rebuilding the provider integration to get either of these is the wrong trade. Upstream already runs each provider's own runtime and tracks its changes.

** Outcome
- Actors are shown as a dock of pictures at the top of the sidebar, whatever project filter is set.
- A person sets a thread's picture from its menu. An agent can pin its own thread and set its own picture.
- Running waves are listed in the sidebar. A wave's room opens as a tab in the right panel, from the sidebar or from the thread that started the wave.
- The stock mobile client keeps working with no change.

* Explicit Non-Goals
- Changing how any provider is run, resumed, compacted or forked.
- Changing upstream's subagents, side chats or delegate tool. They stay where upstream shows them.
- A separate "actor" record. An actor is a pinned thread and nothing more.
- Changing what pinning, snoozing, settling or archiving do.
- Changes to the mobile client.
- A kanban board, a member list or a graph for waves. Room chat comes first.
- Owning wave or room state. The wave daemon owns it.
- A plugin system.
- Sending these changes upstream.

* Domain Model Glossary
** Actors
A person's long-lived agents and how the sidebar shows them.

- Actor :: A thread that upstream lists as pinned: pinned, and neither snoozed nor archived. Pinning a thread makes it an actor. Unpinning it, or settling it, which upstream treats as unpinning, ends that.
  /Avoid/: seat, agent, persona
- Dock :: The grid of pictures at the top of the sidebar that stands in for upstream's pinned section.
  /Avoid/: tray, bar, favourites
- Picture :: What stands for an actor in the dock: one or two characters on a colour, or an image. Every picture is an SVG image, whichever of the two it shows.
  /Avoid/: icon, avatar
- Picture file :: The SVG file that holds one thread's picture. It belongs to the thread, not to its being pinned, so it survives an unpin.
  /Avoid/: picture record, actor file, profile
- Default picture :: What the dock draws for an actor that has no picture file: a monogram of its title, derived the way upstream derives a project's, on a colour derived from its thread ID.
  /Avoid/: placeholder, fallback icon

** Waves
Work that the wave daemon runs and this fork only displays.

- Wave daemon :: The separate process that starts waves and owns their rooms.
  /Avoid/: orchestrator, swarm server
- Wave :: A named group of worker threads started together through the wave daemon to reach one goal.
  /Avoid/: swarm, batch, team
- Room :: The shared conversation of a wave, which every worker and the person can read and post to. A room is not a thread and no agent lives in it.
  /Avoid/: channel thread, board, chat

** Upkeep
- Seam :: A place where the fork edits a file that upstream owns.
  /Avoid/: patch, hook

* Invariants and Hard Constraints
These are rules the fork imposes on itself. Each says how it is checked; one with no check named is held by review only.

- The dock draws at most 20 pictures. Upstream puts no limit on pins, so a person or an agent can pin more. Those further actors are never refused and never dropped: they are reached through an overflow entry in the dock. Reaching the limit is an expected state, not an error. Checked by =splitActorDock= tests.
- The open actor always has a place in the dock. When it would overflow, it takes the last place. Checked by =splitActorDock= tests.
- The dock ignores the sidebar's project filter, so it shows actors from every connected environment. Everything else about which threads count as pinned follows upstream, by calling upstream's own functions. Checked by =selectActors= tests.
- The dock's order is upstream's pin order. The fork stores no order of its own: dragging a picture writes upstream's pin order keys, chosen by upstream's own planner and sent by upstream's own command, so stock T3 Code shows the same order. Checked by =planActorMove= tests and the drag scenario.
- A dropped order shows at once and is held on screen until four seconds after its writes finish. While the writes are in flight no picture can be dragged, so two drops never plan against the same keys. A failed write releases the hold and says so.
- Every seam is listed under [[*Seams]]. An edit to an upstream file that is not listed there is a defect.
- New behaviour goes in new files. A seam is a mount point, a list entry or a single branch, never a rewrite.
- The fork adds no field to upstream's contracts and no database migration.
- The fork's own text is English only. It adds nothing to upstream's translation catalogs, which are generated files that every upstream text change rewrites. Each of its files that holds text says so in a lint comment at its top.
- Whatever the fork stores, it stores as files a person can read and edit, in the environment's state directory beside upstream's database. A dev run and the installed app therefore never share fork state.
- A picture file sits in the state directory's =actors= folder. It is named after its thread ID with every character outside =[A-Za-z0-9._-]= percent-encoded, plus =.svg=. A thread ID is an unrestricted string upstream, so it is never used as a path as it stands. Checked by =actorPictureFileName= tests.
- A picture is at most 128 KiB. One read returns at most 24 pictures. The picture folder holds at most 4096 files; a write that would add one more is refused.
- A picture is only ever shown through an image element, which runs no script and loads nothing the picture points at. The server therefore stores any SVG and sanitises none.
- A picture file that is not a usable SVG reads as absent and is left on disk untouched. Checked by a server test.
- A picture is served by the environment that owns the thread.
- The fork works with the wave daemon absent. Without it, the wave list is empty and nothing else changes.

* Verification Policy
** Upkeep
- =main= mirrors upstream and takes no fork commits. The fork lives on =dock=.
- Upstream is merged into =dock= every week or two. It is merged, not rebased, so a conflict is resolved once.
- After each merge, record the date, the conflicted files and the minutes spent under [[*What We've Proven]]. Three merges in a row that conflict outside the listed seams mean the design is wrong and gets smaller.

** Verification and Acceptance
Upstream's checks apply unchanged: =vp run check:changed= before a commit, and upstream's tests for any file the fork touches.

** TODO Finish proving the dock
The first build works in the real app; see [[*What We've Proven]]. These parts of it are built and not yet seen working there:

- A 21st actor reached through the overflow entry. The split is unit-tested; the entry has never been opened in the app.
- The dock with a second environment connected.
- The tooltip that shows an actor's title and status, and the status dot.
- Setting a picture from an image file. Only letters on a colour has been run.
- A drag from one row of pictures to another. The scenario has three pictures in one row; the sidebar wraps after about six.
- A reorder the server refuses. The dock is written to go back to the server's order and show a message; no test makes a write fail.
- The mobile client still listing the same threads as pinned. The fork changes no contract and no table, so it should; it has not been run.

Known gaps, each a decision the build made to stay small:

- A picture cannot be dragged between the dock and the overflow list. With more than 20 actors, the only way to bring a later one into the dock is to unpin and pin it again, which puts it first.
- Pictures are reordered with a pointer only. There is no keyboard way, and a drag by touch has not been tried.
- The first drag among actors that have never been reordered writes an order key to every actor, one request each. Later drags write one key.
- If the server takes longer than four seconds after a write to report the new order, the dock shows the old order until it does.
- Renaming from a picture's menu opens the thread, where the header renames it. The dock has no title to edit in place.
- Sharing with a guest is missing from a picture's menu. It is still in the open thread's header menu.
- A change an agent makes to its picture file shows when the window next gains focus or the set of actors changes, not at once.
- Deleting a thread leaves its picture file behind. The folder's cap bounds the cost.
- An agent sets its picture by writing its picture file. There is no tool for it: a new tool costs three upstream files, one of them a byte budget every upstream tool change also edits.
- Dragging a row onto the pinned boundary still pins it, but its place among the existing actors is computed against a list with no pinned rows. Where it lands is untested.
- Upstream's next and previous thread keys still step through pinned threads, which now have no row to show which one is open. The dock marks it instead.
- An actor on a machine that runs stock T3 Code shows in the dock with its default picture. That machine has no picture route, so its picture cannot be set from the dialog.

** The daily client and Rex, 2026-11-20
Read from upstream's docs and tags and from the installed Rex command line, version =0.1.0-preview.21=. Nothing here was built.

- The fork may not open the installed app's data today. The installed app last ran as =0.1.11=, and that tag has three database migrations (100 to 102) that the fork's merge base lacks. The fork has to merge upstream to at least the version that last opened the data before it is pointed there. :: =git diff --name-status v0.1.11..00200bd412 -- apps/server/src/persistence/Migrations=
- The fork adds no migration, so a fork build and a stock build made from the same upstream commit can take turns on the same data. A fork built from =main= moves the data ahead of the stable app.
- Upstream builds a macOS app with =pnpm run dist:desktop:dmg:arm64=. Not run. Whether an unsigned local build can sign in to T3 Connect, and how its updater is kept from installing a stock release over it, are not known.
- A dev run in a linked worktree seeds its database from a read-only copy of the installed app's, when that is at most 500 MiB. The main checkout uses =~/.t3/dev= and is not seeded. :: =docs/operations/development.md=, "State and ports"
- Rex has no command that attaches a terminal to a running session. =rex block stream= exists and answers "not implemented". :: =rex --help= and =rex block stream BLOCK=
- Rex's server streams a terminal to a client over a data connection opened with a single-use ticket, under the name =rex.data.terminal.v1=. What travels on it has not been seen. :: =rex api describe data.connect= (Seen later the same day; see [[*The Rex probe, 2026-11-20]].)
- Rex reports, for each terminal, the status its program last gave, such as an agent that is done. It returns a terminal's screen as escape sequences, types text into a terminal, and tells its app to show a session. :: =rex block call -b BLOCK program_status=, =rex api ls=, =rex -C CLIENT actions=
- T3 Code's own terminal draws with libghostty compiled to WebAssembly. :: =ls apps/web/src/terminal/ghostty=
- Upstream already lets an agent that runs outside T3 Code read, start and message threads through the environment's MCP server. It gives such an agent no place in the sidebar. :: =docs/user/outside-agents.md=

** The Rex probe, 2026-11-20
Run against Rex =0.1.0-preview.21=, API revision 18, on a scratch session that the probe created and destroyed. The server had seven sessions before and seven after. The probe script and the test that fed T3 Code's engine were one-off files and are not in the repository. No fork code was written.

- Rex documents its client protocol in full, and each server serves the guide for its own version. The earlier line that nothing was known about the data connection was a failure to look there. :: =curl --unix-socket "$HOME/Library/Application Support/rex/server.sock" http://localhost/llms.txt=
- The guide says it exists "so that you can write your own client". A client names the API revision it was written for and the server translates, from revision 0 to 18. :: the guide, "API Revisions"
- A terminal's stream behaves as the guide says. A control WebSocket attached to the session got a ticket; a second WebSocket sent it and got a 32-byte welcome; then came a snapshot that starts with =GHOSTSNP=, version 1, then one message from Rex giving the terminal's size, then the program's output as ordinary terminal bytes. :: the probe
- Typing goes over the control connection, not the stream. =com.superlogical.terminal.write= passed a raw Ctrl-C to the program. :: the probe
- T3 Code's terminal engine cannot load the snapshot as built. Its Ghostty revision, =3ff6d08f= of 2026-07-07, has no snapshot decoder; Rex builds against =36ec90a0= of 2026-09-30, which has one and needs Zig 0.16 where T3 Code's build script pins 0.15.2. The library vendored for iOS is at =cf8edc23= and already contains the decoder. :: =cat native/libghostty-vt/VERSION=, and =include/ghostty/vt/snapshot.h= at each revision of =ghostty-org/ghostty=
- T3 Code's terminal engine, unchanged, draws a Rex terminal without the snapshot. Rex returns a terminal's screen and scrollback as escape sequences, with its modes when asked. Fed to the engine, that gave the same text, a red and a bold blue cell, 129 lines of scrollback, and the alternate screen and mouse reporting switched on. The stream's bytes after the snapshot then drew live output, and Rex's own messages in them were not shown. :: the probe's captures, fed to =GhosttyTerminalCore= in a unit test
- Painting from the screen text and then following the stream is not exact. Output that arrives between the two reads is drawn twice or not at all. Loading the snapshot is exact, because the stream continues from the snapshot's last byte. The size of that error on a busy agent's screen was not measured.
- While a program holds the alternate screen, the screen text leaves out what is on the primary screen. :: the probe
- A browser cannot open a Unix socket, so T3 Code's server has to stand between a web or mobile client and Rex. T3 Code's own terminals already reach the client as a history string followed by output events, which is the shape the unchanged engine was fed. :: =grep -n "nextTerminalAttachSeedState" apps/web/src/terminal/ghostty/core.test.ts=
- A terminal's owner sets its size and colours for every client, the Rex app included. The probe took no ownership and resized nothing. :: the guide, "How Rex Is Organized"
- Someone has already built a third-party Rex client that draws panes with libghostty from this stream: RexPocket, for Android. Its record framing for the snapshot matched the real bytes. :: =https://github.com/leizhiyuan/rexpocket=
