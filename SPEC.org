#+TITLE: T3 Code fork: actors and waves
#+OPTIONS: num:t

This file specifies what this fork adds to T3 Code. Everything it does not mention is upstream's and is left alone. Upstream's own terms are defined in [[file:docs/internals/glossary.md][docs/internals/glossary.md]]; this spec uses them unchanged and defines only the terms the fork introduces.

* Objective Function
One window for all agent work.

A person who runs many long-lived agents should have each of them one click away, with a face they recognise, wherever they are in the app. The waves those agents start should be visible beside them, and what a wave is saying should be readable without leaving the thread in hand. Underneath, each provider keeps running exactly as upstream runs it.

The fork stays small enough to merge upstream every week or two without dread. Every feature is judged against that.

* Problem and Outcome
** Problem
- Long-lived threads are hard to keep in reach. With twenty or more of them, a list of titles does not scale: they are all "open", and finding one is a search.
- A wave of workers started by one agent has no shared place to talk that is not itself an agent, and no place in the window where a person can watch it.
- Rebuilding the provider integration to get either of these is the wrong trade. Upstream already runs each provider's own runtime and tracks its changes.

** Outcome
- Actors are shown as a dock of pictures at the top of the sidebar, whatever project filter is set.
- A person sets a thread's picture from its menu. An agent can pin its own thread and set its own picture.
- An agent that still runs in Rex has a picture in the dock too. Its picture opens its terminal in the main area, with the sidebar still open, so a person can move agents from Rex to T3 Code one at a time.
- Running waves are listed in the sidebar. A wave's room opens as a tab in the right panel, from the sidebar or from the thread that started the wave.
- The stock mobile client keeps working with no change. It shows thread actors as upstream shows pinned threads, and no Rex actors.

* Explicit Non-Goals
- Changing how any provider is run, resumed, compacted or forked.
- Changing upstream's subagents, side chats or delegate tool. They stay where upstream shows them.
- A separate record for an actor. A thread actor is a pinned thread and nothing more. A Rex actor is a few lines in the dock file and nothing more.
- Running anything in Rex. The fork creates, closes and arranges nothing there. It shows a terminal that Rex already runs, types what the person types, and takes that terminal's size.
- Rex actors in the mobile client.
- Changing what pinning, snoozing, settling or archiving do.
- Changes to the mobile client.
- A kanban board, a member list or a graph for waves. Room chat comes first.
- Owning wave or room state. The wave daemon owns it.
- A plugin system.
- Sending these changes upstream.

* Domain Model Glossary
** Actors
A person's long-lived agents and how the sidebar shows them.

- Actor :: An agent with a place in the dock. It is either a thread actor or a Rex actor.
  /Avoid/: seat, agent, persona
- Thread actor :: A thread that upstream lists as pinned: pinned, and neither snoozed nor archived. Pinning a thread makes it a thread actor. Unpinning it, or settling it, which upstream treats as unpinning, ends that.
  /Avoid/: pinned actor, native actor
- Rex actor :: A terminal that runs in Rex and that the dock file names.
  /Avoid/: external agent, remote agent, Rex session
- Dock file :: The file that names an environment's Rex actors, in the order the dock shows them.
  /Avoid/: config, manifest, registry
- Viewer :: One open view of a Rex actor's terminal in a T3 Code window. Two windows that show the same Rex actor are two viewers.
  /Avoid/: client, tab, attachment
- Dock :: The grid of pictures at the top of the sidebar that stands in for upstream's pinned section.
  /Avoid/: tray, bar, favourites
- Picture :: What stands for an actor in the dock: one or two characters on a colour, or an image. Every picture is an SVG image, whichever of the two it shows.
  /Avoid/: icon, avatar
- Picture file :: The SVG file that holds one actor's picture. A thread's picture file belongs to the thread, not to its being pinned, so it survives an unpin. A Rex actor's picture file is the one the dock file names.
  /Avoid/: picture record, actor file, profile
- Default picture :: What the dock draws for an actor that has no picture file: a monogram of its title, derived the way upstream derives a project's, on a colour derived from its thread ID or its name.
  /Avoid/: placeholder, fallback icon

Rex's own words are used as Rex's guide defines them: a /session/ is a group of work, a /block/ is one terminal in it, a /client/ is a program connected to Rex's server, and a block's /owner/ is the client whose size the terminal follows.

** Waves
Work that the wave daemon runs and this fork only displays.

- Wave daemon :: The separate process that starts waves and owns their rooms.
  /Avoid/: orchestrator, swarm server
- Wave :: A named group of worker threads started together through the wave daemon to reach one goal.
  /Avoid/: swarm, batch, team
- Room :: The shared conversation of a wave, which every worker and the person can read and post to. A room is not a thread and no agent lives in it.
  /Avoid/: channel thread, board, chat

** Upkeep
- Seam :: A place where the fork edits a file that upstream owns.
  /Avoid/: patch, hook

* Interfaces, Data Shapes, and State Transitions
** The dock file
=actors/dock.kdl= in the environment's state directory. A person or an agent writes it. The server only reads it, each time the dock or a viewer asks.

#+begin_src kdl
// Agents that still live in Rex.
rex "scout" {
    session "scout-desk"   // a Rex session's label or ID; the actor's name when left out
    block "claude"         // a terminal's label or ID; the session's focused terminal when left out
    title "Scout"          // what the tooltip and the page say; the name when left out
    picture "scout.svg"    // an SVG file beside this file; the default picture when left out
}
rex "clerk"

// Only needed where Rex does not listen in its usual place.
rex-socket "/path/to/server.sock"
#+end_src

The reader takes the part of KDL that means the same in KDL 1 and KDL 2: nodes, quoted strings, numbers, properties, children, comments, the slashdash, and a backslash that continues a line. It refuses a bare word as a value, raw and multi-line strings, type annotations and the keywords for true, false and null, and says on which line.

** Routes
Both are raw routes beside the picture route, authenticated the way upstream's media routes are.

- =GET /api/actor-dock= returns each Rex actor's name, title and picture, and the dock file's problems with their lines. It does not return which Rex session an actor names.
- =GET /api/rex-terminal?actor=NAME= upgrades to a WebSocket for one viewer.

** A viewer's connection
The viewer sends JSON text messages: =open= with its columns and rows, then =write= with typed text, =resize=, and =own= to take the terminal back. The server sends =seed= once, with the screen as escape sequences, its size, and whether output was seen while the screen was read; then the program's output as binary messages; and =size=, =owner=, =exit= and =error= as JSON.

For each viewer the server opens its own client connection to Rex and, in this order: finds the session and the terminal, takes ownership of the terminal, opens the terminal's output stream and steps over the snapshot it starts with, asks for the viewer's size, reads the screen, sends the seed, and from then on relays the stream. Closing the viewer closes both Rex connections with a close frame, and Rex passes the terminal to the next client in line for it.

* Invariants and Hard Constraints
These are rules the fork imposes on itself. Each says how it is checked; one with no check named is held by review only.

- The dock draws at most 20 pictures, thread actors and Rex actors counted together. Upstream puts no limit on pins, so a person or an agent can pin more. Those further actors are never refused and never dropped: they are reached through an overflow entry in the dock. Reaching the limit is an expected state, not an error. Checked by =splitActorDock= tests.
- The open actor always has a place in the dock. When it would overflow, it takes the last place. Checked by =splitActorDock= tests.
- The dock ignores the sidebar's project filter, so it shows actors from every connected environment. Everything else about which threads count as pinned follows upstream, by calling upstream's own functions. Checked by =selectActors= tests.
- Thread actors come first, in upstream's pin order. The fork stores no order of its own for them: dragging a picture writes upstream's pin order keys, chosen by upstream's own planner and sent by upstream's own command, so stock T3 Code shows the same order. Checked by =planActorMove= tests and the drag scenario.
- Rex actors come after the thread actors, in the order the dock file lists them. A Rex actor's picture is not dragged: its place is its place in the file.
- A dropped order shows at once and is held on screen until four seconds after its writes finish. While the writes are in flight no picture can be dragged, so two drops never plan against the same keys. A failed write releases the hold and says so.
- Every seam is listed under [[*Seams]]. An edit to an upstream file that is not listed there is a defect.
- New behaviour goes in new files. A seam is a mount point, a list entry or a single branch, never a rewrite.
- The fork adds no field to upstream's contracts and no database migration.
- The fork's own text is English only. It adds nothing to upstream's translation catalogs, which are generated files that every upstream text change rewrites. Each of its files that holds text says so in a lint comment at its top.
- Whatever the fork stores, it stores as files a person can read and edit, in the environment's state directory beside upstream's database. A dev run and the installed app therefore never share fork state.
- A picture file sits in the state directory's =actors= folder. It is named after its thread ID with every character outside =[A-Za-z0-9._-]= percent-encoded, plus =.svg=. A thread ID is an unrestricted string upstream, so it is never used as a path as it stands. Checked by =actorPictureFileName= tests.
- A picture is at most 128 KiB. One read returns at most 24 pictures. The picture folder holds at most 4096 files; a write that would add one more is refused.
- A picture is only ever shown through an image element, which runs no script and loads nothing the picture points at. The server therefore stores any SVG and sanitises none.
- A picture file that is not a usable SVG reads as absent and is left on disk untouched. Checked by a server test.
- A picture is served by the environment that owns the thread.
- The server never writes the dock file. Checked by review: =grep -n "dock.kdl\|DOCK_FILE_NAME" apps/server/src/actors/*.ts= shows reads only.
- The dock file is at most 64 KiB, with at most 32 Rex actors, 1024 nodes and blocks nested 8 deep. A line the reader cannot use is reported with its number and skipped; a file it cannot parse lists no actors. Checked by =readDock= and =parseKdl= tests.
- A picture the dock file names is a file name, never a path, and the file sits beside the dock file. Checked by a =readDock= test.
- A viewer names a Rex actor. Which session and terminal that is comes from the dock file alone, read on the server. A viewer cannot name a Rex session.
- A Rex terminal is a shell on the server's machine. Its route needs upstream's terminal scope, and a viewer is closed when its sign-in ends.
- One server holds at most 16 viewers open. Output held while a terminal opens is at most 8 MiB, typing held behind an unanswered write at most 1 MiB, and output queued for a slow viewer at most 16 MiB; past any of these the viewer is closed.
- T3 Code never answers a program's questions to the terminal, such as where the cursor is. Rex's own terminal answers them, and a second answer would be typed into the program.
- Typing reaches Rex one call at a time, each sent after the one before it is answered, because Rex runs separate calls in any order. Checked by a bridge test.
- The fork works with Rex absent. A Rex actor's picture still shows; opening it says that Rex could not be reached.
- The fork works with the wave daemon absent. Without it, the wave list is empty and nothing else changes.

* Fault Model
What can fail at each boundary the Rex actors add, and what the fork does.

| Boundary | What fails | What the fork does |
|----------+------------+--------------------|
| The dock file | It is missing | The dock has no Rex actors. |
| | It does not parse, or is over its size | The dock shows a problem marker that lists the line and the reason. A window that already had the actors keeps them until it is reloaded. |
| | One node is wrong: a bad name, a duplicate, an unknown setting, a picture that is a path | That node or setting is skipped and reported with its line. The rest is used. |
| Rex's server | It is not running, or does not answer within 5 seconds to connect and 8 seconds a call | The viewer is told why and closed. The window tries again after 0.5, 2 and 5 seconds, then offers a button. |
| | Either connection to it drops | The same. Nothing is resumed: a new viewer reads the screen afresh. |
| | The session or the terminal the dock file names is not there, or two sessions share the label | The viewer is told which, and closed. The window does not try again by itself. |
| | The terminal closes in Rex | The viewer is told, and closed. The window does not try again by itself. |
| | Another Rex client takes the terminal | The viewer keeps drawing at the size that client sets, says so, and offers to take it back. |
| | Output arrives while the screen is being read | See below. |
| A viewer | It sends something that is not one of its four messages, or too much | It is closed. |
| | It reads too slowly | It is closed once 16 MiB wait for it. |
| | Its sign-in ends | It is closed, and both Rex connections with it. |

Rex gives the screen in one call and the output on another connection, and nothing ties a place in one to a place in the other. Output received before the screen was asked for is already in the screen, so it is dropped. Output received while that call was in flight may be in the screen or not. So the server waits for output to pause for 40 ms, up to 300 ms, reads the screen, and reads it again if any output arrived during the read, four times at most. If the terminal never pauses, the last screen is sent and the output from its read is drawn after it: that output can show twice until the program next repaints.

This narrows the error and does not remove it. The two connections share no order, so output written just before the read can arrive after the read's answer and be drawn twice, with no output seen during the read. Nothing has compared the drawn screen with Rex's own on a busy terminal. Loading Rex's snapshot instead would be exact with no waiting; see [[*Open Questions]].

* Verification Policy
** Upkeep
- =main= mirrors upstream and takes no fork commits. The fork lives on =dock=.
- Upstream is merged into =dock= every week or two. It is merged, not rebased, so a conflict is resolved once.
- After each merge, record the date, the conflicted files and the minutes spent under [[*What We've Proven]]. Three merges in a row that conflict outside the listed seams mean the design is wrong and gets smaller.

** Verification and Acceptance
Upstream's checks apply unchanged: =vp run check:changed= before a commit, and upstream's tests for any file the fork touches.
